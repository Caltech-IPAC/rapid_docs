# Exercise 2026-11: the rebuild's baseline on every dataset, where the seconds go, and what broke

On 2026-11-08 the rebuild ran once on every dataset at hand, each under
a dataset and run of its own, in the loop's own shape, on the on-demand
prompt queue. The image was the one the stage-timing change registered,
so every job recorded how long its named steps took. This post is the
baseline those runs set: one row per dataset, the seconds per stage
read from `job_metrics`, the stages ranked by what they cost the largest
run, and every failure seen with where it went. The arc's later
investigations measure against these rows and add their own sections
to this page by pull request.

The difference stage is where the time goes. On Russ Laher's 10/21
GBTDS window, 1,980 differences took 2,641.5 of the run's 2,961.5 Batch
vCPU-hours, and the real/bogus scoring and the X path's PSF-fit
catalog together took two thirds of the whole run. Four failures
stopped or spoiled a baseline run, and each has its fix merged: the
publish pool wedge at window scale, the packet job's memory, the
OpenUniverse pointing overflow and the night recipe's missing catalog
imports.

### The ranking

Run 187 is the throughput sample: one loop drained the 10/21 window,
1,980 differences, on `:112`. Every stage reserved one vCPU per job,
so a stage's vCPU-hours are its summed `container_seconds`. Ordered by
share of the run's 2,961.5 vCPU-hours:

1. `rb_s`, real/bogus scoring in the difference job: 1,111.3 vCPU-h, 37.5%.
2. `xsources_s`, the X path's PSF-fit catalog: 844.1 vCPU-h, 28.5%.
3. The difference job's untimed part (the SFFT solve and catalogs among it): 674.2 vCPU-h, 22.8%.
4. The packet job's untimed part: 165.4 vCPU-h, 5.6%.
5. `packet_forced_s`: 54.1 vCPU-h, 1.8%.
6. `packet_cutouts_s`: 38.7 vCPU-h, 1.3%.
7. Intake: 25.4 vCPU-h, 0.9%.
8. Reference: 12.2 vCPU-h, 0.4%.
9. `packet_read_s` 11.2, `packet_assembly_s` 10.4, `gzip_s` 6.8,
   `pixel_columns_s` 5.1 and `packet_matching_s` 2.4 vCPU-h, under 0.4%
   each; psf, import and `refpsf_s` under 0.1 vCPU-h together.

The order holds for GBTDS-like data with many candidates per image. On
the small HLWAS, OpenUniverse and flight samples the difference's
untimed part comes first, since `rb_s` and `xsources_s` scale with the
candidate count. The runs overlapped each other on the queue, so their
seconds are comparable within a run and loosely across runs.

## What broke, and where it went

**Run 177's publish pool wedge** (fixed, rapid PR 558). At window scale
on `:108`, about 800 difference publishers waited in
`pg_advisory_xact_lock(177, …)` inside their publish transactions, each
holding one of the pipeline's 800 pooler server connections, while the
lock holder (job 40630, by inference) sat idle in transaction in
`catalog.attach`'s pair loop. At
10:49 UTC 382 differences failed on `query_wait_timeout`, 1,522 were
still running with none ending after 10:50 UTC, and the loop exited 70
at 11:13 UTC. Runs 173, 179 and 180 failed jobs in the same window. Run
177's 1,613 Batch jobs were terminated 11:24 to 11:26 UTC and the pool
recovered. PR 558 takes the field locks all or none with
`pg_try_advisory_xact_lock`, retrying while holding no connection, and
attaches by declination band. Run 184 proved it at one epoch on `:111`,
run 187 at window scale on `:112`: no lock waiter in 20 samples, 1,161
of 1,980 publishers retried their locks, median try 6, max 81.

**Run 180's packet OOM** (fixed, rapid PR 560). Every F087 packet job, a
2,000-packet set, exited 137 at 2,048 MiB over nine attempts. Resubmitted
at 8,192 MiB they peaked at 2,246 to 2,443 MiB, so the default became
5,120 MiB; run 186 sent all five through at the default on the first
attempt, and run 187's packet peak was 2,752 MiB.

**Run 173's intake overflow** (fixed, rapid PR 556). Four OpenUniverse
intakes (pointings 42982, 44137, 56457, 57227) exited 70 with
`NumericValueOutOfRange`: the reader wrote the pointing as `OBSERVTN`,
which lands in `exposures.observation smallint` and overflows above
32,767. The reader now leaves it undefined, and run 182 took ten of ten
epochs.

**Run 174's loop exit 64** (fixed, rapid_docs PR 180). The night recipe
imported Gaia only, so the loop's first pass admitted nothing without
the NED and NED-LVS imports. The loop page's Starting a night now
registers all three in one import job; run 183 followed it verbatim.

**Validation does not finish at window scale** (recorded on the parked
flow-schema-findings item, not fixed here). Run 158's packets check did
not finish in two hours over 159 GB. Run 187's packets check passed on
a sample of 18 of 1,980 sets and its catalog check was still running at
6,600 s.

**Exposure 5012501** is a reference epoch in run 187 and was differenced
in run 158. The reference bound, 61685.81344, falls 0.2 s after the
exposure, so the loop treats it as reference material in both runs;
run 158 submitted its 18 differences and packet jobs by hand (the
[socsims-1021 post](2026-10-27-socsims-1021.md)). Run 187 has 1,980
differences where run 158 has 1,998 for that reason.

**Batch packed the window's one-vCPU jobs ten to an instance.** Run
187's 1,980 difference jobs ran ten per r6i.8xlarge, with 6,336 vCPU
desired. Recorded for the throughput items.

**The X path's two steps slowed at window scale.** Run 187's `rb_s`
median, 1,984 s, is about 1.8 times run 169's 1,112 s on the pilot's 72
images, and `xsources_s`, 1,529 s, about 1.4 times its 1,067 s.
Recorded for xsources-rb-profile.

**The packet job's untimed part on the window**, 361 s of a 541 s
median and 5.6% of the run, against at most 14 s on every other run.
Seen in this post's reading of `job_metrics`; no timer covers it.

### The gate's holds

The gate judged only the runs with at least `min_epochs` differences
per field. On the others every set went out unjudged: run 174 sent its
three GBTDS gb3 sets, 175, 176, 178 and 179 theirs, and 173 its six. Run 182
held one OpenUniverse set on ring. Run 186 held all five F087 sets on
core (+0.105 to +0.128). Run 187 held 1,977 of the window's 1,980 sets,
1,953 on `core_fraction` and 24 on the S/N > 20 count, and sent 3.

Those holds follow the bounds the gate carries on every dataset, the
HLWAS-derived core ±0.025 and ring ±0.015. Ben kept them on GBTDS on
2026-10-27 (gbtds-gate-core), and whether GBTDS gets bounds of its own
stays on {ref}`the open questions <decision-open-questions>`.

## background: bkgest against photutils

The bkgest binary in the difference stage's background step was
replaced by photutils `Background2D` on branch `exp/bkgest-photutils`
of rapid (`7bb63efd`, from `rebuild` `681b208f`; nothing merged). The
estimator was matched to `[difference.bkgest]` as closely as the two
allow. Boxes are the 500 px grid spacing stretched to tile the 4,088 px
image evenly, 511 px, against bkgest's 501 px windows on 500 px nodes.
There is one 2.5 sigma clip about the median, with bkgest's scale (half
the 15.9 to 84.1 percentile range), then the mean. There is no median
filter. Boxes more than half masked are excluded, against bkgest's 50%
bad-pixel tolerance. A first-order zoom stands in for bkgest's bilinear
map. The reference is still background-subtracted by the same
estimator (`subtract_from_reference`), its uncovered pixels excluded
and given back.

Both legs replayed the baseline runs' own difference jobs on this host,
one at a time, in the `rapid-rebuild:112` image (`41d671e7`; the branch
differs from it only in this step). The replay, the branch's
`scripts/replay_difference.py`, reads each job's inputs and settings
read-only and publishes nothing. The jobs were run 175's null epoch
(job 35799), run 176's injected passes 4 to 6 (35903 to 35905) and
run 174's gb3 epoch 2014201 (35900). The bkgest leg is the image's own
code. Its counts are within 4 of the Batch jobs' on every HLWAS epoch
and equal on gb3, and that is this measurement's spread.

Background maps, photutils minus bkgest, in ADU. "Net" is the science
map's difference minus the reference map's, the part that reaches the
difference image. The scatter is 1.4826 times the median absolute
deviation. Bright stars are the bkgest leg's subtracted science pixels
above 50 sigma, dilated 15 px: 2.5% of HLWAS pixels and 90% of gb3's.
Crowded and quiet cells are the top and bottom quartiles of the 64

to the background, and on these two epochs it reaches the counts by

## xsources and rb

Two named steps, `rb_s` and `xsources_s`, took 66% of run 187's
vCPU-hours. `rb_s` is RuBR-AT scoring of SFFT's two PSF-fit catalogs.
`xsources_s` is the xsources' PSF fit plus their own RuBR-AT scoring,
so it holds rb seconds too. This section profiles both on one run 187
difference job, reproduced on this host, and measures three leads on
that job's own inputs. The leads are on branch `exp/xsources-rb` of
rapid (`98a342fe`, from `rebuild` `681b208f`). Nothing is merged.

The job is 46889 (exposure 5033601, SCA 3, F146), the nearest to the
run's 4,736 s median `container_seconds`. The replay ran in the
`rapid-rebuild:112` image (`41d671e7`), its threads pinned to one core
by `taskset`, with the job definition's 24 GiB and the image's thread
variables (only `OPENBLAS_NUM_THREADS=1`). The driver is the branch's
`scripts/xsources_rb/replay_job.py`. It runs the stage's `run(job)` on
the job's own row, inputs and run settings and publishes nothing; the
stage drew one `diffimages` pid. Its SFFT PSF-fit catalogs (every
column, `rb_score` and `rb_label` among them) are equal to the ones
Batch published for the job, and its `xsources` and `sources` rows are
equal but for `pid`. Each lead re-ran the replay's own `_score_rb` or
`_xsources_columns` call on a copy of that call's inputs, one after
another on one pinned core. Other cards shared the host, at load 4 to
18.

The replay was much faster than Batch, and part of that is not one
core. onnxruntime 1.31 opens 16 pool threads on this 16-vCPU host.
It pins 15 of them to vCPUs 1 to 15 whatever the process's affinity,
so the default replay scored on up to 16 cores: 6,670 CPU seconds in a
1,611 s wall. The one-thread column (`RAPID_EXP_ORT_THREADS=1`, scores
identical) is the job's real one-vCPU cost. Even so, Batch took 4.6
times as long for `rb_s` and 1.45 times for `xsources_s`.

Two causes fit and neither is verified. One is co-tenancy: Batch
packed ten of these jobs per r6i.8xlarge, and each job's onnxruntime
would pin its pool to the same vCPUs 1 to 15. The other is the vCPU:
this host is an m8a.4xlarge, where a vCPU is a whole AMD EPYC 9R45
core, and an r6i vCPU is one hyperthread of a 3.5 GHz Intel core. The
first would explain why scoring slowed more than the fit, which runs
on one thread. The same may explain run 169 to 187's slowdown, `rb_s`
1,112 to 1,984 s, but that was not chased.

At one thread, no inference lead moved the scoring beyond the spread
between runs (555.7 to 634.1 s, with the host's load between 4 and
18). Inference is compute-bound and already batched, so batch size and
spinning change nothing that matters. What onnxruntime's thread count
changes is how many cores scoring takes, not its CPU cost.

The fit in one process is identical and no slower: on one vCPU the
shipped two forked processes buy nothing.

The batched fit takes the same boxes, weights, initial aperture flux
and model as photutils. It uses the spline's analytic derivatives where
photutils' TRF takes finite differences, and it is 2.2 times faster.
It is not identical, and it is not close. On the positive xsources only
11.8% of `x_fit` agree within 0.01 px, and `flux_fit` differs by a
median of 13.8 flux errors. Under one model, it reaches a lower χ² than
photutils' solution on 1,836 of the first 2,000 sources. photutils
warns on this job that fits "may not have converged". By that χ², its
TRF fits appear to stop short of the minimum on most of these
candidates; this is inferred, not verified.

What this measures and does not:

- Speed: the job's two X path steps are about 1,154 s on one local
  vCPU against 3,509 s on Batch, and scoring is almost all of them.
  Batch's extra time is placement or hardware. Neither cause was
  isolated.
- Inference: no setting tried makes scoring cheaper per source. A
  cheaper model or runtime (a quantised or graph-optimised export)
  would change the scores and was not tried.
- Fit: the identical lead saves 3 s. The batched fit's disagreement
  is the fit's own convergence, measured here and not judged.
