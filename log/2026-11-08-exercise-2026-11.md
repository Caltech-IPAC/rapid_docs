# Exercise 2026-11: the rebuild's baseline on every dataset, where the seconds go, and what broke

On 2026-11-08 the rebuild ran once on every dataset at hand, each under
a dataset and run of its own, in the loop's own shape, on the on-demand
prompt queue. The image was the one the stage-timing change registered,
so every job recorded how long its named steps took. This post is the
baseline those runs set: one row per dataset, the seconds per stage
read from `job_metrics`, the stages ranked by what they cost the largest
run, and every failure seen with where it went. The arc's later
investigations measure against these rows and add their own sections
to this page by pull request.

The difference stage is where the time goes. On Russ Laher's 10/21
GBTDS window, 1,980 differences took 2,641.5 of the run's 2,961.5 Batch
vCPU-hours, and the real/bogus scoring and the X path's PSF-fit
catalog together took two thirds of the whole run. Four failures
stopped or spoiled a baseline run, and each has its fix merged: the
publish pool wedge at window scale, the packet job's memory, the
OpenUniverse pointing overflow and the night recipe's missing catalog
imports.

### The ranking

Run 187 is the throughput sample: one loop drained the 10/21 window,
1,980 differences, on `:112`. Every stage reserved one vCPU per job,
so a stage's vCPU-hours are its summed `container_seconds`. Ordered by
share of the run's 2,961.5 vCPU-hours:

1. `rb_s`, real/bogus scoring in the difference job: 1,111.3 vCPU-h, 37.5%.
2. `xsources_s`, the X path's PSF-fit catalog: 844.1 vCPU-h, 28.5%.
3. The difference job's untimed part (the SFFT solve and catalogs among it): 674.2 vCPU-h, 22.8%.
4. The packet job's untimed part: 165.4 vCPU-h, 5.6%.
5. `packet_forced_s`: 54.1 vCPU-h, 1.8%.
6. `packet_cutouts_s`: 38.7 vCPU-h, 1.3%.
7. Intake: 25.4 vCPU-h, 0.9%.
8. Reference: 12.2 vCPU-h, 0.4%.
9. `packet_read_s` 11.2, `packet_assembly_s` 10.4, `gzip_s` 6.8,
   `pixel_columns_s` 5.1 and `packet_matching_s` 2.4 vCPU-h, under 0.4%
   each; psf, import and `refpsf_s` under 0.1 vCPU-h together.

The order holds for GBTDS-like data with many candidates per image. On
the small HLWAS, OpenUniverse and flight samples the difference's
untimed part comes first, since `rb_s` and `xsources_s` scale with the
candidate count. The runs overlapped each other on the queue, so their
seconds are comparable within a run and loosely across runs.

## What broke, and where it went

**Run 177's publish pool wedge** (fixed, rapid PR 558). At window scale
on `:108`, about 800 difference publishers waited in
`pg_advisory_xact_lock(177, …)` inside their publish transactions, each
holding one of the pipeline's 800 pooler server connections, while the
lock holder (job 40630, by inference) sat idle in transaction in
`catalog.attach`'s pair loop. At
10:49 UTC 382 differences failed on `query_wait_timeout`, 1,522 were
still running with none ending after 10:50 UTC, and the loop exited 70
at 11:13 UTC. Runs 173, 179 and 180 failed jobs in the same window. Run
177's 1,613 Batch jobs were terminated 11:24 to 11:26 UTC and the pool
recovered. PR 558 takes the field locks all or none with
`pg_try_advisory_xact_lock`, retrying while holding no connection, and
attaches by declination band. Run 184 proved it at one epoch on `:111`,
run 187 at window scale on `:112`: no lock waiter in 20 samples, 1,161
of 1,980 publishers retried their locks, median try 6, max 81.

**Run 180's packet OOM** (fixed, rapid PR 560). Every F087 packet job, a
2,000-packet set, exited 137 at 2,048 MiB over nine attempts. Resubmitted
at 8,192 MiB they peaked at 2,246 to 2,443 MiB, so the default became
5,120 MiB; run 186 sent all five through at the default on the first
attempt, and run 187's packet peak was 2,752 MiB.

**Run 173's intake overflow** (fixed, rapid PR 556). Four OpenUniverse
intakes (pointings 42982, 44137, 56457, 57227) exited 70 with
`NumericValueOutOfRange`: the reader wrote the pointing as `OBSERVTN`,
which lands in `exposures.observation smallint` and overflows above
32,767. The reader now leaves it undefined, and run 182 took ten of ten
epochs.

**Run 174's loop exit 64** (fixed, rapid_docs PR 180). The night recipe
imported Gaia only, so the loop's first pass admitted nothing without
the NED and NED-LVS imports. The loop page's Starting a night now
registers all three in one import job; run 183 followed it verbatim.

**Validation does not finish at window scale** (recorded on the parked
flow-schema-findings item, not fixed here). Run 158's packets check did
not finish in two hours over 159 GB. Run 187's packets check passed on
a sample of 18 of 1,980 sets and its catalog check was still running at
6,600 s.

**Exposure 5012501** is a reference epoch in run 187 and was differenced
in run 158. The reference bound, 61685.81344, falls 0.2 s after the
exposure, so the loop treats it as reference material in both runs;
run 158 submitted its 18 differences and packet jobs by hand (the
[socsims-1021 post](2026-10-27-socsims-1021.md)). Run 187 has 1,980
differences where run 158 has 1,998 for that reason.

**Batch packed the window's one-vCPU jobs ten to an instance.** Run
187's 1,980 difference jobs ran ten per r6i.8xlarge, with 6,336 vCPU
desired. Recorded for the throughput items.

**The X path's two steps slowed at window scale.** Run 187's `rb_s`
median, 1,984 s, is about 1.8 times run 169's 1,112 s on the pilot's 72
images, and `xsources_s`, 1,529 s, about 1.4 times its 1,067 s.
Recorded for xsources-rb-profile.

**The packet job's untimed part on the window**, 361 s of a 541 s
median and 5.6% of the run, against at most 14 s on every other run.
Seen in this post's reading of `job_metrics`; no timer covers it.

### The gate's holds

The gate judged only the runs with at least `min_epochs` differences
per field. On the others every set went out unjudged: run 174 sent its
three GBTDS gb3 sets, 175, 176, 178 and 179 theirs, and 173 its six. Run 182
held one OpenUniverse set on ring. Run 186 held all five F087 sets on
core (+0.105 to +0.128). Run 187 held 1,977 of the window's 1,980 sets,
1,953 on `core_fraction` and 24 on the S/N > 20 count, and sent 3.

Those holds follow the bounds the gate carries on every dataset, the
HLWAS-derived core ±0.025 and ring ±0.015. Ben kept them on GBTDS on
2026-10-27 (gbtds-gate-core), and whether GBTDS gets bounds of its own
stays on {ref}`the open questions <decision-open-questions>`.

## background: bkgest against photutils

The bkgest binary in the difference stage's background step was
replaced by photutils `Background2D` on branch `exp/bkgest-photutils`
of rapid (`7bb63efd`, from `rebuild` `681b208f`; nothing merged). The
estimator was matched to `[difference.bkgest]` as closely as the two
allow. Boxes are the 500 px grid spacing stretched to tile the 4,088 px
image evenly, 511 px, against bkgest's 501 px windows on 500 px nodes.
There is one 2.5 sigma clip about the median, with bkgest's scale (half
the 15.9 to 84.1 percentile range), then the mean. There is no median
filter. Boxes more than half masked are excluded, against bkgest's 50%
bad-pixel tolerance. A first-order zoom stands in for bkgest's bilinear
map. The reference is still background-subtracted by the same
estimator (`subtract_from_reference`), its uncovered pixels excluded
and given back.

Both legs replayed the baseline runs' own difference jobs on this host,
one at a time, in the `rapid-rebuild:112` image (`41d671e7`; the branch
differs from it only in this step). The replay, the branch's
`scripts/replay_difference.py`, reads each job's inputs and settings
read-only and publishes nothing. The jobs were run 175's null epoch
(job 35799), run 176's injected passes 4 to 6 (35903 to 35905) and
run 174's gb3 epoch 2014201 (35900). The bkgest leg is the image's own
code. Its counts are within 4 of the Batch jobs' on every HLWAS epoch
and equal on gb3, and that is this measurement's spread.

Background maps, photutils minus bkgest, in ADU. "Net" is the science
map's difference minus the reference map's, the part that reaches the
difference image. The scatter is 1.4826 times the median absolute
deviation. Bright stars are the bkgest leg's subtracted science pixels
above 50 sigma, dilated 15 px: 2.5% of HLWAS pixels and 90% of gb3's.

## xsources and rb

Two named steps, `rb_s` and `xsources_s`, took 66% of run 187's
vCPU-hours. `rb_s` is RuBR-AT scoring of SFFT's two PSF-fit catalogs.
`xsources_s` is the xsources' PSF fit plus their own RuBR-AT scoring,
so it holds rb seconds too. This section profiles both on one run 187
difference job, reproduced on this host, and measures three leads on
that job's own inputs. The leads are on branch `exp/xsources-rb` of
rapid (`98a342fe`, from `rebuild` `681b208f`). Nothing is merged.

The job is 46889 (exposure 5033601, SCA 3, F146), the nearest to the
run's 4,736 s median `container_seconds`. The replay ran in the
`rapid-rebuild:112` image (`41d671e7`), its threads pinned to one core
by `taskset`, with the job definition's 24 GiB and the image's thread
variables (only `OPENBLAS_NUM_THREADS=1`). The driver is the branch's
`scripts/xsources_rb/replay_job.py`. It runs the stage's `run(job)` on
the job's own row, inputs and run settings and publishes nothing; the
stage drew one `diffimages` pid. Its SFFT PSF-fit catalogs (every
column, `rb_score` and `rb_label` among them) are equal to the ones
Batch published for the job, and its `xsources` and `sources` rows are
equal but for `pid`. Each lead re-ran the replay's own `_score_rb` or

The replay was much faster than Batch, and part of that is not one
core. onnxruntime 1.31 opens 16 pool threads on this 16-vCPU host.
It pins 15 of them to vCPUs 1 to 15 whatever the process's affinity,
so the default replay scored on up to 16 cores: 6,670 CPU seconds in a

Two causes fit and neither is verified. One is co-tenancy: Batch
packed ten of these jobs per r6i.8xlarge, and each job's onnxruntime
would pin its pool to the same vCPUs 1 to 15. The other is the vCPU:
this host is an m8a.4xlarge, where a vCPU is a whole AMD EPYC 9R45
core, and an r6i vCPU is one hyperthread of a 3.5 GHz Intel core. The
first would explain why scoring slowed more than the fit, which runs
on one thread. The same may explain run 169 to 187's slowdown, `rb_s`
1,112 to 1,984 s, but that was not chased.

shipped two forked processes buy nothing.

The batched fit takes the same boxes, weights, initial aperture flux
and model as photutils. It uses the spline's analytic derivatives where
photutils' TRF takes finite differences, and it is 2.2 times faster.
It is not identical, and it is not close. On the positive xsources only
11.8% of `x_fit` agree within 0.01 px, and `flux_fit` differs by a
median of 13.8 flux errors. Under one model, it reaches a lower χ² than
photutils' solution on 1,836 of the first 2,000 sources. photutils
warns on this job that fits "may not have converged". By that χ², its
TRF fits appear to stop short of the minimum on most of these
candidates; this is inferred, not verified.

What this measures and does not:

- Speed: the job's two X path steps are about 1,154 s on one local
  vCPU against 3,509 s on Batch, and scoring is almost all of them.
  Batch's extra time is placement or hardware. Neither cause was
  isolated.
- Inference: no setting tried makes scoring cheaper per source. A
  cheaper model or runtime (a quantised or graph-optimised export)
  would change the scores and was not tried.
- Fit: the identical lead saves 3 s. The batched fit's disagreement
  is the fit's own convergence, measured here and not judged.

### On Batch

The 4.6 times above is co-tenancy, through onnxruntime's threads. A
Batch difference job asks for one vCPU, but its container has no CPU
quota: `cpu.max` reads `max 100000`, and the weight is 100. No job of
either arm below was throttled even once. onnxruntime sizes its pool from
the host's core count, 32 on an r6i.8xlarge. So each job's scoring takes
whatever cores are idle and competes with every other job on the host
that does the same. The suspected 1-vCPU quota does not exist. The
thread count matters by how many jobs on one host multithread, not by any
limit on each one.

Underneath that sits a second, smaller gap. At one thread a Batch
job's scoring is CPU-bound (CPU equals wall) at 46 ms per scored source.
On the local m8a.4xlarge core it is 14.7 ms. That 3.2 times does not move
with co-tenancy, so it is the r6i vCPU (one hyperthread of an Ice Lake
core, its sibling likely busy) against a whole Zen 5 core. This is
inferred, not isolated: the sample ran on r6i only.

The read is from rapid's `exp/xsources-rb` (`647e4106`), whose
`scripts/xsources_rb/batch/` holds the scripts.

#### The read

- **The cause is co-tenancy among multithreaded scorers.** The default
  arm's cost per score rises from 16 ms with almost no default-thread
  neighbours, to 30 ms, to 45 ms with four to six of them, and run 187's
  nine default neighbours give 67 ms. The one-thread arm does not move
  with its neighbours (rho −0.18). That is the 4.6 times: job 46889
  scored at 68 ms per source among nine default-thread jobs against 14.7
  ms locally at one thread.
- **Ruled out: a CFS quota or throttling.** There is none, and no
  period was throttled.
- **Ruled out: the instance-type split within r6i.** The 4xlarge and
  8xlarge jobs of the one-thread arm cost 44.0 and 46.6 ms.
- **Not isolated: the hardware.** The one-thread floor of 46 ms against
  14.7 ms locally points to the r6i vCPU (inferred). A Batch run on m8a,
  or on r6i with its siblings idle, would separate it.
- **The default arm is not efficient, only faster.** It spends 210 ms
  of CPU per score against 46 ms at one thread: 4.5 times the CPU,
  mostly pool threads competing for the same cores. It is faster per
  job only while neighbours leave cores idle.

**The thread setting does not merge.** It is not identical (the
1.2e-7 differences above). It is not faster on Batch in the mix
measured: one thread's median `rb_s` is 1.23 times the default's, and
equal to it only at four to six default neighbours. A run with every job
at one thread was not measured. From the one-thread floor it would
score at about 46 ms per source against run 187's 67, but that is an
extrapolation from the arm, not a measurement. Whether it earns the
setting is the next measurement, and the bar's "identical" would then
need a tolerance ruling.

## Instance type

Which Batch instance types run the difference job fastest, and at what
price? This section answers from the Exercise runs' records first, then
from one controlled sample on six one-type lanes.

The seconds follow generation and the scorer's thread pool. They do not
follow vendor. Several results are measured, not inferred:

- **Generation.** A 7th-generation type runs a difference 15 to 17 % faster
  than a 6th-generation one at one scorer thread on an idle host.
- **The default thread pool.** It scores about 3.5 times faster on the
  Intel types than at one thread when one other job shares the host, and
  about twice as fast on the AMD types. At four neighbours it gains nothing.
- **Bytes.** They split on AVX-512, not on vendor. Every AVX-512 type,
  the AMD m7a among them, writes byte-identical source and xsources rows
  and scores. The m6a, the one type without AVX-512, differs from them on
  73 % of its source rows.
- **Price.** The cheapest difference is the r 4xlarge's at one thread,
  five jobs a host. An m7i at the default pool costs the same and takes
  half the wall time.

### The sample

The sample was run 187's SCA 3: 110 differences, F146, with their
intakes, references and packet sets. It ran under run 187's settings
(the same layers) on six temporary one-type On-Demand lanes in the
`rapid-batch-types` stack (rapid_systems PR 504). Each lane was a
compute environment of one 4xlarge type and a queue, with up to twelve
instances and nothing else on the hosts. Each lane ran three arms, each
under its own dataset (`itp-<type>-<arm>`) and its own live run with its
own catalog bindings:

- **alone**: the first 16 differences by expid at one onnxruntime
  thread, the difference and packet jobs asking for the node's 16 vCPU,
  so one job per host;
- **packed**: all 110 at one thread, at the shipped 1 vCPU and 24 GiB
  ask. That fits two differences on an m 4xlarge and five on an r
  4xlarge. The first 16 are also tabled on their own, for the
  comparison with the other two arms;
- **default**: the first 16 at the shipped ask and onnxruntime's default
  thread pool, the workload as it ships.

Default and alone ran first, side by side; packed ran after the default
arm's loop had drained, so no one-thread job shared a host with a
default-thread one.

The image was rapid `exp/xsources-rb` `0ff43536`, registered as
`rapid-rebuild:114`. That is ort-threads-batch's probe plus four more
things:

- phase walls: before SFFT, the SFFT call (`rb_s`, `xsources_s` and the
  pixel columns are inside it) and after it;
- the host CPU as the container sees it: threads per core from cpu0's
  sibling list (what `lscpu` reports), vendor, model, and the AVX-512
  and AMX flags;
- the launcher's per-stage vCPU ask for the alone arm;
- a newer base. Its `pip list` (263) equals `:113`'s, and its `rpm -qa`
  (192) differs by rapid-awaicgen 5.4-5 → 5.4-6, which rapid_systems
  rebuilt from its source tree. Every arm ran on this image, so the

- **Family, m against r.** They show no difference beyond the packing:
  r6i equals m6i and r7i equals m7i alone at one thread, within 1 %.
- **Packing at one thread.** On the m lanes (two differences to a host)
  packed equals alone within 4 % on the same 16. On the r lanes (five
  to a host, about four neighbours) packed is 8 % slower: r6i 2,729 s
  against 2,529, and r7i 2,294 against 2,120. Five one-thread jobs fit
  in eight physical cores, so the 8 % is presumably shared memory
  bandwidth or cache rather than SMT siblings; that cause is unverified,
  since neither was measured.
- **SMT.** It is not isolated. The m7a, the one type at one thread per
  core, sits where its generation puts it.
- **The default pool against one thread.** At one neighbour (the m
  lanes) the default arm's `rb_s` is 0.26 to 0.54 of the one-thread
  arm's on the same 16, and the whole difference 0.53 to 0.66. At four neighbours (the
  r lanes) it is 0.88 (r6i) and 1.08 (r7i) of the whole difference: no gain, the
  ort-threads-batch result.

What the libraries already do: OpenBLAS 0.3.34 (pthreads) and
onnxruntime's MLAS dispatch AVX-512 or AVX2 kernels at run time, so an
AVX-512 host gets its wide kernels without a rebuild. The C tools
(SExtractor, SFFT's helpers, awaicgen) build at `-O2` without `-march`,
so they use no AVX-512 on any host. A `-march=x86-64-v4` build would be
the one hardware-specific optimization left in the C tools. It was not
measured; their time sits inside "before SFFT" and "SFFT and catalogs",
about a quarter of the job.

#### Recommendation

This is not applied. `rapid-batch.yaml`'s list is the team's model of
Batch's cost, and a change to it is its own item.

- **The instance list:** AVX-512 types only, which drops m6a. Its rows
  differ from every other type's, so a run placed partly on m6a is not
  reproducible on the rest of the list. It is also the slowest type.
  This removes the Determinism line's vendor split.
- **Prefer the 7th generation,** m7i and r7i, 15 to 17 % faster at a
  5 % higher hourly rate than m6i and r6i. The m7a is byte-equal to
  them, but at the default pool it scores twice as slowly as m7i at a
  15 % higher rate, so it earns no place first.
- **The `VCPU` ask:** ask for what the default thread pool uses rather
  than 1. At the shipped 1 vCPU and 24 GiB, the memory packs two
  differences on an m 4xlarge and five on an r 4xlarge. At two, the
  default pool is twice as fast as one thread (m7i 1,185 s, $0.133 a
  difference). At five, it gains nothing (r7i 2,468 s, $0.145). An
  ask of half an m 4xlarge (`VCPU 8` beside 24 GiB) makes every host
  pack as the m lanes did, so the wall halves at the price of r7i's
  one-thread packing (r7i packed $0.131 at 2,234 s). This row is the
  m-lane default arm, measured; an explicit `VCPU 8` ask was not run.

#### The kernels

The evidence comes from the bench's alone arm. Its scorer's main thread
(one thread, so all the scoring) had its instruction pointer read by
`ptrace` every 20 ms: 13,172 samples. Each sample's 32 bytes were
disassembled. onnxruntime's profiler and verbose log ran on the first
1,024 sources.

| r7i.4xlarge, alone arm | Samples | zmm (AVX-512) | xmm only (SSE) | Neither |
|---|---|---|---|---|
| onnxruntime | 12,915 (98.0 %) | 8,226 (64 %) | 4,200 (33 %) | 489 |
| libc, numpy, Python | 257 | 113 | 29 | 115 |

- **The convolutions are MLAS's AVX-512F kernels.** The hottest regions
  are `vfmadd231ps zmm` loops with `vbroadcastss zmm` and `vshuff32x4`:
  MLAS's NCHWc convolution and its reorders. The NchwcTransformer
  rewrites every convolution as `Conv…_nchwc` with `ReorderInput` and
  `ReorderOutput`. These are 56 % of kernel time in the profile.
- **A third of the samples are 128-bit SSE.** `mulps`, `subps` and
  `xorps` on xmm, four floats a step, in a few 4 KiB regions outside
  MLAS. The profile names them as the elementwise Mul (20.5 %), Neg
  (5.9 %), Sub (5.7 %) and Add (2.3 %), together 34 % of kernel time:
  the model's GELU (`x · ½ · (1 + erf(x/√2))`) is exported unfused, so
  its Muls run in onnxruntime's generic elementwise code at the wheel's
  baseline. Its Erf (6.6 %) is an MLAS zmm kernel. No Gelu fusion
  (`GeluFusionL1`, `GeluFusionL2`, `FastGeluFusion`, `BiasGeluFusion`)
  matches the graph.
- **Precision is fp32.** Every float tensor in the profile is `float`;
  the int32 and int64 ones are the survey and filter tokens and shapes.
- **Unused on the r7i:** AMX and AVX512-BF16 (the CPU has
  `amx_tile` and `avx512_bf16`), because the model is fp32 and
  MLAS's fp32 path does not use them. Also unused: the zmm width in
  the elementwise ops.
- **The m8a (Zen 5) agrees:** 77 % zmm and 19 % SSE, the same regions.

#### The rebuild

- **A source build with other flags or `-march`** would not change the
  convolutions. MLAS dispatches its kernels at run time from CPUID, and
  the profile shows it already runs the AVX-512F path. It could compile
  the generic elementwise loops wider, which is the 34 % share. Those
  loops stream (256, 32, 64, 64) float tensors, 128 MiB each, far past
  the cache. A wider loop is bounded by memory bandwidth, so the gain is
  well under that share. It was not measured: a source build of
  onnxruntime is a package build, outside this item's envelope.
- **OpenMP or another threading pool** changes nothing at one thread:
  the session then runs no pool threads, and the scoring is all on the
  calling thread (every sample above is that thread's).
- **Leads that need no rebuild**, each recorded and not applied:
  - An export that fuses the GELU into onnxruntime's `Gelu` (MLAS,
    AVX-512) would move its Erf and Muls, at most 27 % of kernel time,
    into one kernel. That is a model change, so its scores must be read
    against the bar.
  - A smaller batch keeps the elementwise tensors in cache: batch 64 was
    4 % faster and identical (xsources-rb-profile).
  - A bf16 or int8 model would reach AMX, but that is a precision ruling.

### Structure

The question: where in the pipeline's structure and code do the
host-hours go, and which change buys the most per image for its cost?
This is a plan from the records only. Nothing was edited, and no run
was submitted. Runs 213 and 214 got their first report here
(`scripts/throughput_report.py`); their Batch records are saved under
the outputs root's `throughput-report/`.

**The unit.** Every gain is in host-hours per image, an image being
one difference (one SCA of one exposure). The baseline is run 216
(`rapid-rebuild:119`, rapid `e7d7155a`, every setting as shipped,
24,576 MiB, all r7i). It used 18.3 host-hours of its own for 110
images, 0.166 per image; the difference job took 15.46 of them, 0.141
per image. A difference job-hour cost 0.204 host-hours there, about
4.9 jobs to a host.

Run 216 predates the onnxruntime settings (rapid 574). So `rb` is
re-read at the merged setting from run 214 (`exp/ort-settings`
`156e6117`, `:118`, the code PR 574 merged). Its difference jobs ran
77.84 job-hours, and the four scoring calls took 55.84 of them
(71.7 %). At run 216's 0.204 that is 0.144 host-hours per image for
the difference and 0.104 for `rb`.

Run 214's host-hours are not used directly. It shared its hosts with
run 213 (two thirds or more of their span belonged to other runs).
The equal split then charged it 22.2 host-hours against run 213's 13.5, for job-hours
1.25 times as long.

the records support only a bound. The leads overlap, so their gains do
not add. Most leads' host-hours shrink by the same factor at a denser
packing (memory-shape-15g), so the order holds there too;
difference-vcpus is the exception, since its gain depends on the packing.

**The merged setting's cost at a light packing.** Runs 213 (the

### Memory diet

The question: what holds the difference job's anonymous working set,
and can it shrink by a packing step with every output unchanged? The
anon peak is what an ask must hold. At the derivation's allocatable
memory, the asks that change packing are 15,360 MiB (4 jobs per 64 GiB,
16 per 256), 12,800 (5 and 20), 10,600 (6 and 24) and 9,100 (7 and 28).
A lead counts only when it crosses one.

**One lead, SFFT's subtraction pass, takes the job from the first step
to the last.** On run 212's job 66156 the anon peak goes from 15,014 to
6,238 MiB, with every output equal at full precision. It is merged in
rapid PR 576 (`03f79e9c`). The ask is unchanged, and the lower ask is Ben's to grant
(the for-Ben line `memory-diet-step`).

#### The lead

`Kab_Wla[a]` is `Wl ** a`, and `Wl` depends on the row alone; `Wm` on
the column alone. `modules/sfft/sfft_lowmem.py` (rapid PR 576) runs the
subtraction pass with one column of the first stack and one row of the
second. They are computed by the library's own expressions on the same
coordinates, 2.4 MiB in all. The library's compiled `Construct_FDIFF`
reads them through zero-stride views. Every other step is the
library's, in its order and through its compiled kernels. The
conjugates, which subtraction never reads, are not made. The solve pass
is the library's own. `sfft_rapid_crowded.py` installs it with one
import. A unit test holds the pass bit for bit against the library's on
two synthetic frames.

### Publish ANALYZE

The question: with the publisher's post-commit `ANALYZE` removed, does
the fakesrc window drain at 15,360 MiB with no attempt killed, and what
are its host vCPU-hours per image against run 187's 5.25?

**The cause, read on run 215.** The publisher ran its post-commit
`ANALYZE` statements in one transaction, in table-name order, so a
plain table came first: `diffimages` for a difference, `external` for
a packet. `ANALYZE` takes a `ShareUpdateExclusiveLock`, which conflicts
with itself, and keeps it until the transaction ends. So each
publisher held that first lock through its whole sequence, about 26
fields' children of four tables plus its `sources` and `xsources`
children (the largest, `xsources_20271007_3`, holds 50 M rows in
12 GB). Every other publisher of the stage waited in line, each
holding a pooler connection. The live read caught the end of run 215's
queue at 04:39 UTC (`pg_stat_activity`, `pg_locks`,
`pg_blocking_pids`). One packet job, 10 m 44 s into its transaction,
was running `ANALYZE "packets_4723688"`. 122 sessions waited on
`external` in one chain, each blocked by every session ahead of it,
and the chain drained at about one tail a second. Difference 73649 is
one example: its stage ended at 01:27, it took its field locks at
01:52, and its tail ended at 03:21.

What held `ANALYZE "xobjects_4637679"` from 01:39 to 03:20 is not
recoverable. SMDC runs with `log_lock_waits = off` and without
`pg_stat_statements`, and its log for the night holds only WAL
archiving, checkpoints, and autovacuum's cancels and skips. The queue
alone accounts for the stall: 1,980 difference tails, ending within an
hour of each other, ran one at a time.

**The fix: no tail at all** (rapid PR 581, `35766464`; the design page,
rapid_docs 202). The card's first option held, so the publisher runs
nothing after its publishing commit, and autovacuum keeps the
statistics. Before the merge, the check ran every child-level read the
difference and packet stages make under `EXPLAIN (ANALYZE)`. Each read
ran on a never-analysed temp copy of a real child, standing for a
fresh one, and again after `ANALYZE` of the copy. The copies held one
job's rows and 20 jobs' rows. The worst read was the packet's own rows
from an `xsources` child: 131 ms fresh against 82 ms analysed, once a
job. Every other read differed by under 10 ms, and the plans differed
only in scan choice. On the proof run, autovacuum analysed 2,070 of the
2,194 children the run wrote during the window, plus `diffimages`,
`official`, `external` and `l2files`, and no child was over its
threshold at the end.

**The proof: run 219** (`pubanalyze-fakesrc-1021`). It is run 187's
inputs and run 215's settings: run 187's layers and four `--set`s, with
the difference at 15,360 MiB by default now. It ran on
`rapid-rebuild:123` (rapid `35766464`, image `sha256:27558201…`) on
`rapid-queue-prompt`, started at 05:05 UTC after run 215's last job had

the gate. A sampler read `pg_stat_activity` and `pg_locks` every 5 s

### Reference frame order

The question: can a reference built from the same inputs come out the
same in every run, whatever order the run intakes those inputs?

**The fix, held** (rapid PR 584, `exp/reference-frame-order` at
`8eec0324`, not merged). `read_frames` broke an `mjdobs` tie by `rid`,
the run's intake order. It now breaks it by `dev`'s key: the frame
centre's distance from the tile centre (`get_overlapping_l2files`,
`order by b.mjdobs, dist`), then the file name. The order and the
`max_frames` cut then follow the inputs alone.

**The proof.** Field 4686831 (SCA 13) is one of the 19 fields of runs
215 and 219 whose cut moved. It has 38 candidate frames on SCAs 13 and
17, with each exposure's two frames tied on `mjdobs`, and 18 SCA 13
epochs. Its inputs were intaken twice, each into a dataset and live run
of its own, on `rapid-rebuild:125` with run 219's settings body. Run
223 intaken SCA 13 first and run 224 SCA 17 first, so every tied pair
